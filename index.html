Android in-app inspector library

Inspect your Android app from inside the app.

AppInspect is a drop-in Android library for developers, testers, and product teams who need real app evidence during development and QA. Open a built-in inspector inside your app and review network traffic, local storage, background jobs, crashes, and runtime metadata without building a custom debug panel.

Who it is for

A practical debugging surface for real Android teams.

Use AppInspect when a bug report needs more than screenshots and logs. It helps developers reproduce faster, helps QA attach better evidence, and helps companies standardize internal diagnostics across Android apps.

Developers and QA engineers

Faster debugging from the exact build being tested.

  • Inspect OkHttp calls with filters, search, payload previews, and cURL generation.
  • Validate SharedPreferences, DataStore, SQLite, WorkManager, crashes, and runtime metadata.
  • Open through shake, launcher shortcut, long press, notification tap, or AppInspect.open(context).
Companies and private app teams

A reusable library instead of a one-off internal screen.

  • Give teams the same inspector experience across apps and environments.
  • Adopt from Maven Central with normal Gradle dependency management.
  • Configure entry points, panels, raw-value visibility, editing tools, and retention for your rollout.
Inspector tools

Six inspection areas in one Android library.

AppInspect is built around the views developers and testers reach for first: API calls, on-device data, background work, crashes, runtime context, and simple ways to open the inspector.

N

Network

OkHttp request and response capture with headers, payload previews, timing, filters, search, cURL, TXT export, and HAR export.

S

Storage

SharedPreferences inspection and editing, read-only DataStore Preferences, and SQLite or Room database browsing with SQL console.

W

WorkManager

Read-only work-spec visibility for states, tags, unique names, attempts, constraints, input, output, and progress data.

C

Crashes

Fatal exception capture with exception type, message, thread name, timestamp, stack trace, copy, share, and clear actions.

R

Runtime

App metadata, configured environment, build tier, device details, session data, and custom metadata sections.

U

Inspector UI

Built-in full-screen inspector with open paths for direct calls, shake, launcher shortcut, long press, and notification taps.

Integration

Install by build variant, not as a blanket dependency.

The recommended setup gives internal builds the full inspector and production builds only the no-op OkHttp counterpart. That keeps shared OkHttp builder code simple without pulling inspection code into release APKs.

1

Add Maven Central

Resolve AppInspect from a shared repository so every developer and CI runner uses the same artifact.

settings.gradle.kts 
dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
    }
}
2

Add the library

Use the full inspector in debug builds. Use the no-op artifact in release builds when you want shared OkHttp setup without inspection behavior.

build.gradle.kts 
dependencies {
    debugImplementation("io.github.suryansh1720001.appinspect:appinspect:<latest-version>")
    releaseImplementation("io.github.suryansh1720001.appinspect:appinspect-no-op:<latest-version>")
}

For custom variants like staging or internal QA, add the full appinspect artifact to that variant only when your team needs it. Check Maven Central for the latest published version.

3

Attach OkHttp capture

The same builder code compiles across variants. In release, the no-op returns the builder unchanged.

OkHttpClient 
val client = OkHttpClient.Builder()
    .addAppInspectInterceptor()
    .build()

Guard direct AppInspect.open() or AppInspect.install() calls by build variant, because the no-op artifact only mirrors the OkHttp API surface.

Configuration

Customize AppInspect for your team workflow.

The default setup is developer-friendly. When the build is shared with a wider QA or business audience, you can hide raw values, disable editing tools, turn off request notifications, or remove panels that are not needed.

Controlled QA profile

AppInspectConfiguration 
AppInspect.install(
    application = application,
    configuration = AppInspectConfiguration(
        entryPoints = AppInspectEntryPoints(
            networkNotificationsEnabled = false,
        ),
        powerTools = AppInspectPowerTools(
            showRawSensitiveValues = false,
            allowSharedPreferencesEditing = false,
            allowDatabaseEditing = false,
            allowSqlConsole = false,
        ),
    ),
)

Configuration levers

showRawSensitiveValues
When false, configured headers, query parameters, body fields, cookies, and metadata keys are masked or removed before storage.
allowDatabaseEditing and allowSqlConsole
Keep database inspection read-focused for QA builds that do not need mutation tools.
networkNotificationsEnabled
Disable request notifications when device lock-screen visibility or shared testers are a concern.
Security and data handling

A local library, not an external data service.

AppInspect runs inside your Android application. It does not require an AppInspect cloud account, does not upload captured app data to an AppInspect backend, and does not send telemetry from your users. Data stays on the device by default unless someone copies or shares an export from the app.

What the library does by default

  • Captured network and crash data stay on device by default in app-private SQLite.
  • Storage and WorkManager information is read from the host app on demand for the inspector UI.
  • Network log export happens only when a user triggers TXT, HAR, copy, or Android share-sheet actions.
  • The export FileProvider is scoped only to cacheDir/appinspect_exports/.
  • AppInspectActivity is declared with android:exported="false".
  • Host SQLite operations use parameterized queries; the SQL console is the explicit developer power tool.
  • DataStore inspection is read-only and never writes to .preferences_pb files.

Production and company controls

  • Use releaseImplementation with appinspect-no-op when release builds should have no inspector UI, no storage access, and no captured data.
  • The no-op OkHttp surface is pass-through, so shared client-builder code can stay clean across debug and release variants.
  • Mask sensitive values with showRawSensitiveValues = false and custom redaction rules.
  • Disable SharedPreferences editing, database editing, SQL console, network notifications, or crash capture when a team does not need them.
  • Keep enabled builds limited to trusted development, QA, internal test, or controlled company distribution paths.
QA checklist

Share evidence carefully. Exports can carry real credentials.

Network exports are valuable for bug reports, but they include the same headers and tokens the original requests used. Treat them as internal security artifacts.

Before sharing TXT, HAR, or cURL output

  1. Search for Authorization, Cookie, Set-Cookie, X-API-Key, and app-specific credential headers.
  2. Replace token values with [REDACTED] before uploading to Jira, Slack, email, shared drives, or bug trackers.
  3. Remove -H "Authorization: ..." flags from cURL commands copied into tickets or messages.
  4. If an unredacted export was already shared, rotate the exposed token and ask the backend team to invalidate the session.

Distribution guidance

  • Give debug, internal, or QA builds only to trusted users who are allowed to see internal app data.
  • Turn raw visibility off for wider QA audiences with showRawSensitiveValues = false.
  • Disable storage editing and SQL console unless the tester genuinely needs mutation access.
  • Remember that crash stack traces reveal package names, class names, methods, and line numbers.
  • Exports persist in app cache until Android clears cache or the app is uninstalled.
